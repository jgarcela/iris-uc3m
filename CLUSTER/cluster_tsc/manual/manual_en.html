1. Introduction

SLURM is the resource manager and job scheduler used in the DTSC cluster. Its main purpose is to allocate shared computing resources —CPU, memory, nodes and GPUs— in an orderly way among users and research groups.

Centralized management

It avoids conflicts between users and makes it possible to define usage policies by partitions, accounts and QoS.

Optimization

It adjusts the allocation of CPUs, memory, time and GPUs to the actual needs of each job.

Smart queues

It prioritizes short jobs, debugging jobs, standard jobs, long jobs or GPU jobs according to the cluster policy.

Traceability

It makes it possible to check who ran a job, when it ran, which resources were used and what the result was.

2. System access

To submit jobs to the SLURM cluster, users must connect to the machines authorized for their working group. From those machines, scripts are prepared and jobs are submitted using sbatch, srun, salloc or through the launcher library based on launch_process.py y Scheduler.py.

3. Preparing working environments

Users may use the preinstalled and optimized libraries available on each machine, or prepare isolated Python environments with venv o Conda.

For environments, data and results, it is recommended to use shared volumes such as /extot/usuarios01/USER o /extot/clusterdata/USER, so that files are available from the nodes where tasks are executed.

Python environment with venv

mkdir -p /extot/clusterdata/$USER/venvs
python3 -m venv /extot/clusterdata/$USER/venvs/my_environment
source /extot/clusterdata/$USER/venvs/my_environment/bin/activate
python -m pip install --upgrade pip
pip install numpy scipy pandas scikit-learn torch

Conda environment

conda create -p /extot/clusterdata/$USER/conda/envs/my_environment python=3.11
conda activate /extot/clusterdata/$USER/conda/envs/my_environment
conda install numpy scipy pandas scikit-learn
Recommendation: place environments on shared volumes such as /extot/usuarios01/USER o /extot/clusterdata/USER, so that they are available from the nodes running the job.

6. Definition of parameter sweep tasks using JSON files

One common problem when running experiments based on parameter sweeps with a large number of parameter combinations is automating their submission, monitoring and retrying in case of failure.

Based on the former MESOS scheduler, the Python library launch_process.py + Scheduler.py has been migrated to work with the new SLURM scheduler. This new version ensures compatibility with old experiment definitions, adapting them so that they can be launched directly without changes. However, there is a change in behavior regarding temtoary file locations and system queries.

NOTE: This new version must be executed with Python 3.9 or later, unlike the old launcher, which ran with Python 2.7.

Launching experiments

Once the JSON configuration file has been defined, the experiment is launched using the launch_process.py. This tool generates all parameter combinations, submits the tasks to SLURM and monitors their execution until the framework finishes.

python3 ./launch_process.py -c CONFIGURACION.json

If the file launch_process.py has execution permissions (0755), it can be run directly:

./launch_process.py -c CONFIGURACION.json

The file CONFIGURACION.json contains the full experiment definition: cluster connection, resources, variable parameters, static parameters and framework behavior.

Extra parameters may also be passed from the command line to override values defined inside the JSON file. To list all available options:

python3 launch_process.py --help

CPU/GPU compatibility: if no GPUs are requested and a GPU queue partition is configured, the jobs will be rejected. If GPUs are requested and a non-GPU queue partition is configured, the jobs will remain in PENDING waiting for resources that the partition cannot provide.

Section tasks

The section tasks is a dictionary that defines the base task name, the command to run, the variable sweep parameters and the static parameters common to all executions.

KeyDescription
task_basenameName used to identify each task submitted to remote nodes. The name is built from task_basename plus the task identifier and the total number of tasks.
cmdbaseSyntax of the command to execute. It is a Python-based string whose values between braces are replaced by individual values from var_parameters or by static variables defined in parameters.
The program or script to execute must:
  • Be specified using its full PATH
  • Have its containing directory included in the environment variable PATH
  • Be located in the working directory defined by the variable workdir defined in the section framework.
var_parametersVariable parameters for each command to execute. A combination of all variables defined here will be used to generate all tasks. Values may be lists of numeric values, strings, or Python expressions that automatically generate data lists, for example range(inicio, final, paso), np.arange(...), os.getcwd() or other expressions that allow sequences to be built programmatically.
parametersStatic task parameters. These values are common to all generated commands.
 
"tasks": {
  "task_basename": "DeepAutoencoder",
  "cmdbase": "{baseprogram} --lr {learning_rate} --epochs {numepochs} --batch-size {batchsize}",
  "var_parameters": {
    "learning_rate": [
      0.00000000100,
      0.00000000101,
      0.00000000102,
      0.00000000103,
      0.00000000104,
      0.00000000105
    ]
  },
  "parameters": {
    "baseprogram": "/usr/bin/python3 mnist_pytorch.py",
    "database": "MNIST",
    "numepochs": 10,
    "batchsize": 250,
    "localdir": "/extot/clusterdata/USER/data_test",
    "shared_dir": "/extot/clusterdata/USER/autoencoder/results"
  }
}

With these parameters, the commands to execute will be automatically generated by replacing the variables defined between braces ({}) with the values set in the fields var_parameters y parameters. For example, the first two generated commands would be:

/usr/bin/python3 mnist_pytorch.py --lr 0.00000000100 --epochs 10 --batch-size 250
/usr/bin/python3 mnist_pytorch.py --lr 0.00000000101 --epochs 10 --batch-size 250

And so on until all values defined in the list learning_rate. When several variables exist inside var_parameters, the system will automatically generate all possible combinations among them, creating an independent task for each parameter combination.

Task count calculation: the total number of generated tasks will be the product of the number of values defined for each variable included in var_parameters.
learning_rate : 6 values
batchsize     : 4 values
optimizer     : 3 values

Total tasks = 6 × 4 × 3 = 72

Key framework

The key framework is a dictionary that defines the commands and execution environment for each of the remote processes launched on worker nodes.

KeyDescription
nameFramework name.
max_num_procs_simultaneosMaximum number of simultaneous processes. Use -1 to avoid limiting the number of processes.
max_failed_tasksMaximum number of tasks that may fail before declaring the framework failed. 0: at the first failure, the full execution is stopped. n>0: up to n tasks may fail before stopping the framework. -1: failed tasks are reassigned and the framework is not stopped by individual failures.
environment_varsDictionary with environment variables that will be defined in each remote process. For Matlab processes, it is necessary to extot HOME.
urisVector with the set of files that will be distributed to each remote process.
stdoutFile where the console output of the master process will be stored launch_process.py.
stderrFile where the error output of the master process will be stored launch_process.py.
notification1 if an email should be sent when tasks finish.
emailDestination email address when notification is 1. The email will be sent from cluster@tsc.uc3m.es.
max_num_task_per_hostMaximum number of simultaneous tasks per host. This is useful when each process needs a specific tot and only a certain number of processes may run on the same machine.
workdirDirectory where processes will run. Scripts and execution libraries will be found there and, unless another variable is defined, log files for each process will be saved there. If not defined, workdir will be assumed to be the current directory from which launch_process.py.
logdirDirectory where logs for each task will be stored. If not specified, it will be the same as workdir.
 
"framework": {
  "name": "Matlab example",
  "max_num_procs_simultaneos": -1,
  "max_failed_tasks": 0,
  "environment_vars": {
    "MATLABPATH": "/extot/usuarios01/USUARIO/matlab",
    "HOME": "/extot/usuarios01/USUARIO"
  },
  "stdout": "stdout.log",
  "stderr": "stderr.log",
  "notification": 1,
  "email": "USUARIO@tsc.uc3m.es",
  "max_num_task_per_host": 3,
  "workdir": "/extot/clusterdata/USUARIO/experimentos/matlab",
  "logdir": "/extot/clusterdata/USUARIO/experimentos/matlab/logs"
}

This example configures a framework named Matlab example. The maximum number of simultaneous processes is defined with max_num_procs_simultaneos=-1, so the number of processes launched in the cluster is not limited.

The maximum number of failed tasks is set with max_failed_tasks=0, indicating that the framework must stop at the first failed task. The dictionary environment_vars extots the variables MATLABPATH y HOME; in Matlab experiments it is necessary to define HOME.

The variables stdout y stderr, if defined, indicate the files to which the standard output and error output of the program will be redirected launch_process.py. Si notification es 1, an email will be sent to the address indicated in email from the account cluster@tsc.uc3m.es. La variable max_num_task_per_host limits how many simultaneous tasks can run on the same node; in the example, at most 3 tasks per host.

Note on compatibility with old configurations: this example uses a historical MESOS-based configuration through an identifier master of type zk://..., in order to illustrate backward compatibility of the launching tool. Although the example still works without modifications, new configurations should use the SLURM REST-based definition:
"cluster": {
  "master": "https://subserver2.tsc.uc3m.es:6820",
  "queue": "gpus",
  "qos": "normal_gpu"
}

The tool automatically detects legacy MESOS-based configurations and internally adapts them to work on SLURM, but it is recommended to progressively migrate experiments to the new format.

Migration note: old files may contain a master of type zk://... used by MESOS. Although it is recommended to update this variable to the new SLURM REST-based format, for example https://subserver2.tsc.uc3m.es:6820, the tool automatically detects whether it is an old configuration and redirects execution to the default main SLURM server. In this way, old experiments can continue to be launched without modifying the JSON file, although it is recommended to progressively migrate them to the new format.

8. Basic SLURM commands

1) Submitting scripts

# Submit a script
sbatch trabajo.slurm

# Submit to a specific partition
sbatch --partition=main --account=general --qos=normal trabajo.slurm

# Submit to a GPU partition
sbatch --partition=gpus --account=gpu --qos=normal_gpu --gres=gpu:1 trabajo.slurm

# Request a specific GPU model, if defined in GRES
sbatch --partition=gpus --account=gpu --qos=normal_gpu --gres=gpu:MODELO:1 trabajo.slurm

2) Checking job states

# Show the current user queue
squeue -u $USER

# Show a specific job and the waiting reason
squeue -j JOBID -o "%.18i %.9P %.30j %.8u %.2t %.10M %.6D %R"

# Detailed information
scontrol show job JOBID
StateMeaning
PD / PENDINGThe job is queued waiting for resources, priority, permissions or partition conditions.
R / RUNNINGThe job is running.
CG / COMPLETINGThe job is finishing and cleaning up resources.
CD / COMPLETEDThe job completed successfully.
F / FAILEDThe job failed.
CA / CANCELLEDThe job was cancelled.
TO / TIMEOUTThe job exceeded the assigned time limit.
OOM / OUT_OF_MEMORYThe job exceeded the requested memory.

3) Cancelling jobs

scancel JOBID
scancel -u $USER
scancel --name nombre_del_trabajo

4) Cluster information

sinfo
sinfo -Nel
scontrol show partition
scontrol show node NOMBRE_NODO

5) History and accounting

# Recent user jobs
sacct -u $USER --format=JobID,JobName,Partition,Account,QOS,State,Elapsed,MaxRSS,ExitCode

# Efficiency of a completed job
seff JOBID

6) Interactive jobs

# Interactive CPU session
srun --partition=debug --account=debug --qos=debug \
     --cpus-per-task=2 --mem=4G --time=01:00:00 --pty bash

# Interactive GPU session
srun --partition=gpus_debug --account=gpu --qos=debug_gpu \
     --gres=gpu:1 --cpus-per-task=4 --mem=16G --time=01:00:00 --pty bash

9. Troubleshooting

Jobs in PENDING state

If a job remains in PENDING, check the exact reason with the column %R:

squeue -j JOBID -o "%.18i %.9P %.30j %.8u %.2t %.10M %.6D %R"
scontrol show job JOBID
Common reasonWhat to check
ResourcesThere are not enough free CPUs, memory, nodes or GPUs. Reduce requested resources or wait.
PriorityThere are higher-priority jobs ahead.
PartitionTimeLimitThe requested time exceeds the partition/QoS maximum.
AssocGrpGRES o límites de GPUGPU limits have been reached by QoS, account or user.
InvalidAccount / QOSThe specified account or QoS is not valid for that partition.

Common output errors

SLURM writes standard output and errors to the files configured with --output y --error. If they are not specified, a file is usually generated slurm-JOBID.out in the directory from which the job was submitted.

tail -f /extot/clusterdata/$USER/logs/mi_trabajo-JOBID.out
tail -f /extot/clusterdata/$USER/logs/mi_trabajo-JOBID.err

stdout and stderr files in the same working directory (workdir)

Symptom: The working directory fills up with files slurm_XXXXXX.out y slurm_XXXXXX.err

Unlike the APACHE MESOS system, where stdout and stderr output files were generated in the sandbox on each execution agent, in SLURM they are generated, unless otherwise specified, in the same working directory workdir.

Solution:

  • Define in the section framework of the file json> the variable logdir, indicating the directory where stdout and stderr files should be stored.
  • Pass the command-line parameter --logdir, which specifies the directory for stdout and stderr files. This parameter takes precedence over the variable logdir defined in the file json.
Typical errors: Python environment not activated, libraries not installed on the execution node, incorrect relative paths, missing permissions, insufficient memory, time limit exceeded or incorrect GPU request.

11. Best practices

Recommendations

  • Always test with --qos=debug before submitting long jobs.
  • Use descriptive names for your jobs with --job-name.
  • Specify correctly the memory and CPUs you need.
  • Use absolute paths in your scripts.
  • Store logs in organized directories.
  • Implement checkpoints in long training runs.
  • Monitor resource usage with seff after execution.
  • Use virtual environments on shared disks.
  • Document your scripts with clear comments.

Avoid doing

  • Connecting directly by SSH to compute nodes.
  • Running heavy jobs on the main node.
  • Requesting more resources than you actually need.
  • Leaving jobs in the queue indefinitely if you no longer need them.
  • Using virtual environments, data or results in non-shared local paths. Use /extot/usuarios01/USER o /extot/clusterdata/USER.
  • Not specifying time limits.
  • Ignoring error messages in logs.
  • Submitting multiple identical jobs without control.
  • Not cleaning temtoary files after finishing.

12. Recommended job script template

#!/bin/bash
#SBATCH --job-name=descriptive_name
#SBATCH --partition=main
#SBATCH --account=general
#SBATCH --qos=normal
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=4
#SBATCH --mem=8G
#SBATCH --time=02:00:00
#SBATCH --output=/extot/clusterdata/%u/logs/%x-%j.out
#SBATCH --error=/extot/clusterdata/%u/logs/%x-%j.err

set -euo pipefail

echo "Job: $SLURM_JOB_NAME"
echo "Job ID: $SLURM_JOB_ID"
echo "Node(s): $SLURM_JOB_NODELIST"
echo "Initial directory: $(pwd)"
echo "Start date: $(date)"

mkdir -p /extot/clusterdata/$USER/logs

cd /extot/clusterdata/$USER/proyectos/my_project

# Activate environment, if needed
source /extot/clusterdata/$USER/venvs/my_environment/bin/activate

# Run application
